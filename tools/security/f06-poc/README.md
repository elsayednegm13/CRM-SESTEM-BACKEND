# F06 Proof-of-Concept — Tenant SQL Anchor (SECURITY-REMEDIATION-IMPLEMENT-01)

**Status: POC only. Not production code. Not wired into Laravel, migrations, or any
protected environment (G2 / RM02 / DEV / Old TEST / scratch / host:5432).**

This directory is self-contained and talks only to a disposable, newly created
PostgreSQL 16 container created for this task:

- container: `daleel-f06-poc01-pg-7e21poc01`
- network: `daleel-f06-poc01-net-7e21poc01` (bridge, new)
- volume: `daleel_f06_poc01_pg_data_7e21poc01` (new)
- database: `daleel_f06_poc01_synthetic`
- port: `127.0.0.1:55441` (loopback only, not `0.0.0.0`, not reused from any
  existing project port — 55432/55433/55437/55439 remain untouched)

## What this proves

1. **Baseline (`leads_baseline`)** reproduces today's real architecture for the
   `leads` table (migration `2026_10_23_000036_create_leads.php`): a single
   shared runtime role, RLS predicate anchored only on
   `current_setting('app.tenant_id', true)` (a GUC any SQL on that connection
   can rewrite with `set_config(...)`). Used only to confirm the vulnerability
   is reproducible outside G2, on a schema built from scratch.

2. **Fix candidate (`leads_fixed`)** replaces the GUC anchor with a **per-tenant
   LOGIN role** (`poc_runtime_tenant_a` / `poc_runtime_tenant_b`). RLS policies
   are scoped `TO` each role and never reference `app.tenant_id`. A holder of
   tenant A's SQL credential cannot read/write tenant B's rows no matter what
   GUC values they set, because the policy that would let them in simply does
   not exist for their role.

3. **Actor layer (`poc_actor_bound_grants`)** is unchanged from the product's
   real design: still anchored on `current_setting('app.user_id', true)`. This
   POC deliberately does **not** claim to fix actor-level impersonation inside
   the same tenant — T06 is expected to demonstrate this is still open
   (`ACTOR_ISOLATION = OPEN`). See the report for why: one tenant role still
   services every staff member of that tenant, so GUC-level actor identity is
   still forgeable by anyone holding that tenant's SQL credential.

## Files

- `001_baseline_vulnerable.sql` — roles + `leads_baseline` schema/RLS (today's pattern).
- `002_fix_tenant_anchor.sql` — roles + `leads_fixed` schema/RLS (per-tenant anchor) + `poc_actor_bound_grants`.
- `003_fixtures.sql` — synthetic tenants/staff/rows (2 tenants, 2 staff in tenant A, 1 in tenant B, no real data).
- `run_tests.sh` — runs T01–T12 against the running container and prints PASS/FAIL per case (no secrets printed).
- `REPORT_EVIDENCE.md` — sanitized raw command/result log generated by `run_tests.sh` (no passwords).

## Re-running on a *new* sandbox only

**Never point these scripts at G2, RM02, DEV, Old TEST, scratch, or
`host:5432`.** To rebuild from zero on a fresh disposable container:

```bash
docker network create --driver bridge <new-unique-net-name>
docker volume create <new-unique-volume-name>
docker run -d --name <new-unique-container-name> \
  --network <new-unique-net-name> \
  -v <new-unique-volume-name>:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD="$(cat /path/to/local/onetime/superuser.pw)" \
  -e POSTGRES_DB=daleel_f06_poc01_synthetic \
  -p 127.0.0.1:<new-unique-loopback-port>:5432 \
  --memory=512m postgres:16
```

Then apply `001`, `002`, `003` in order with a superuser connection (role
creation needs it), generate fresh one-time passwords for
`poc_runtime_tenant_a` / `poc_runtime_tenant_b` locally (never commit them),
and run `run_tests.sh` with those passwords exported as environment
variables (`PGPOC_TENANT_A_PW`, `PGPOC_TENANT_B_PW`, `PGPOC_ACTOR_A2_PW` is
not needed — actor impersonation in T06 is performed *as* `poc_runtime_tenant_a`
itself, by forging the GUC, not via a separate login).

## Known limits (do not overclaim)

- `SYNTHETIC_SCHEMA_FIDELITY = SCOPED_EQUIVALENT`: this is a minimal schema
  mirroring the real `leads` RLS predicate shape and GUC names, not a replay
  of migrations 001–038. No `tenants`/`tenant_staff_users` tables, no
  triggers, no SECURITY DEFINER functions were reproduced.
- Connection pooling behavior (PgBouncer) is **not** modeled; the product
  does not currently document one in use (`NOT_VERIFIED` in prior reports).
- This POC does not touch Laravel, `config/database.php`, `.env`, routes,
  controllers, or any existing migration.
- A real rollout of this anchor requires solving per-tenant role
  provisioning/rotation and connection-pool sizing with growing tenant
  count — **not attempted here**, this is a security-boundary proof only.
