# Security baseline

- Global identity is distinct from tenant, membership, role, permission, subscription, and provider capability. `users` has no `tenant_id`. A user has at most one ACTIVE company membership, enforced by a PostgreSQL partial unique index. Company requests resolve that membership server-side; zero and anomalous multiple memberships deny. Public registration and customer provisioning are not implemented.
- Browser auth uses official Laravel Sanctum stateful SPA middleware, server-side sessions, HttpOnly session cookies, SameSite=Lax, and CSRF via `/sanctum/csrf-cookie`. Local HTTP proof alone sets Secure=false; non-local environments require HTTPS and Secure=true. Cookie Domain stays unset/host-only unless the approved deployment topology requires a reviewed top-level domain.
- Only the exact local origins `http://localhost:3000`, `:3001`, and `:3002` are credentialed CORS origins. No wildcard is used. Non-local origins require explicit environment configuration and review.
- Login treats unknown, wrong-password, and disabled identities alike publicly. Passwords use Argon2id, are hidden from serialization, and are never logged. Reset tokens are hashed at rest and single-use. Successful login rotates the session ID; `auth_version` changes revoke existing sessions on their next request.
- Authentication and security logs contain event, request ID, safe subject ID when known, result, route template, and method. Passwords, email payloads, tokens, authorization headers, cookies, and request bodies are excluded.
- High-risk current tenant role/membership mutations now append a durable security audit row in the same PostgreSQL transaction. The ordinary runtime audit role is INSERT-only under ENABLE+FORCE RLS, without generic SELECT/UPDATE/DELETE; the structured logs remain diagnostic. See `docs/SECURITY_AUDIT.md`. No public audit browser, provider identity or production retention policy exists yet.
- In non-local environments require HTTPS, secure cookies, approved host/domain scope, trusted-proxy IP lists, secret-manager injection, exact CORS origins, `APP_ENV=production`, and `APP_DEBUG=false`. Trust no proxy or host wildcard by default. Add HSTS only on production HTTPS. JSON APIs do not receive a frontend HTML CSP.
- PostgreSQL is the intended database. Redis is the intended cache, lock, rate-limit, queue, and staging/production session backend. Local auth proof uses file sessions. A cache is never financial authority; future tenant cache keys must include tenant identity.
- No personal access token schema/issue flow or business auth policy is present. Control 10B adds an isolated provider session and TOTP/recovery-code MFA under `/api/v1/super`; see `docs/PROVIDER_SECURITY.md`. It exposes no provider registration, password reset, provisioning, or recovery API. 07B tenant RBAC has five foundation capabilities and a versioned company-admin template, with no public provisioning or mutation endpoints. Company-admin grant is nondelegable in ordinary mutation flows. Template revisions do not silently change instantiated roles.
- Authorization defaults to deny and recomputes from active user, membership, role, grant, and catalog rows inside the tenant guard. The effective-admin invariant checks those same active states under the tenant write lock; role, membership, and global user disable operations cannot leave an active company without one. `TEAM` and `NONE` are reserved deny states. Raw SQL and catalog administration require separate privileged controls.
- TenantContext is readonly and stored only on the current request. A guarded tenant repository rechecks global identity, membership version/status, and tenant state under transaction locks before data access. Future tenant-owned modules must use tenant-scoped access, composite tenant FKs, resource policy checks, and negative A/B tests. RLS protects the five current tenant tables under a non-owner runtime role; future business tables still need their own policies and A/B proof.
- Future worker jobs must re-resolve current actor authority for each attempt and clear context in `finally`. Tenant cache keys, private storage paths and exports must include verified tenant UUID; live Redis/S3 and jobs were not implemented in 07A.
- Dependency readiness probes are opt-in and read-only (`SELECT 1`, Redis `PING`). Public health responses never include connection details.
- Security response headers include `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and a restrictive `Permissions-Policy`. HSTS is production + HTTPS only. CSP is owned by HTML frontends.

- RlsDatabaseContext sets transaction-local database context inside the guarded operation. RLS isolates tenant rows but does not replace RBAC, object authorization or SQL-injection prevention. Global users/reference tables stay outside tenant RLS; see docs/RLS_ARCHITECTURE.md.
