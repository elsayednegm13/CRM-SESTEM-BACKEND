# Provider control operations (10C)

This is the operational company provisioning and company-admin recovery foundation. It does not implement billing eligibility, payment state, tenant business modules, workers, or email delivery. `ACTIVE` is operational activation only.

## Direct first-administrator provisioning

The FND-ID-03 Control-01 Provider API flow is the authorized V1 path. The Provider requests an idempotent `company.provision` operation with a fresh step-up, first-admin display name and tenant-local email, bounded reason/ticket, and an `Idempotency-Key`. A different intent under the same key is rejected. The existing independent reviewer approves the exact digest; self-review is rejected. The execution request supplies the initial password only at execution time. It is Argon2id-hashed into `tenant_staff_users`; the plaintext is never persisted in the operation, audit, or outbox.

One `pgsql_provider_control` transaction creates the `PROVISIONING` tenant, registers its immutable hostname, inserts the first ACTIVE tenant-local staff identity and membership with Provider-operation provenance, creates the genuine `company_admin` v1 role from its active catalog template, assigns it with Provider-operation provenance, appends the staff security event and Provider audit, and changes the tenant to `ACTIVE` only after proving the active `company.administer @ ALL_TENANT` grant and hostname mapping. Failure rolls the complete operation back. The flow writes no founder invitation, token, invitation outbox message, or global `users` row. The same canonical staff email is allowed in a different tenant.

The routes are `POST /api/v1/super/provisioning-operations`, the existing independent approval route, and `POST /api/v1/super/provisioning-operations/{operation}/execute`. Provider routes require an exact Origin and exact direct HTTP Host configured through `PROVIDER_API_HOSTS`; an empty Host list denies all. Forwarded-host headers are not authority. This local implementation does not prove production hostname, TLS termination, or proxy configuration.

### Pending provision revision and withdrawal (migration 28)

`PATCH /api/v1/super/provisioning-operations/{operation}` accepts `expected_revision`, the five current non-secret fields (`display_name`, `slug`, `timezone`, `first_admin_email`, `first_admin_display_name`), and optional `edit_reason`. Unknown fields, including credentials, identities, expiry and idempotency fields, are rejected. The original requester needs current `company.provision` and step-up; the operation and approval must both be pending and unexpired. A normalized no-op returns the current revision and does not change an earlier revision reason. A material edit increments the revision, changes the intent digest and reviewer reference in one transaction, stores an optional reason encrypted with Laravel's authenticated `Crypt::encryptString()` under the existing application key, appends immutable revision metadata and a value-free audit event. The reason is annotation metadata, not part of the provisioning intent digest or audit metadata. Missing or whitespace-only reasons are stored as NULL. The original expiry, requester, approval identifier, reason, ticket and idempotency key stay fixed.

`GET /api/v1/super/provisioning-operations/{operation}/revisions` returns at most 50 chronological revision records with `revision`, `created_at`, the existing requester actor identifier, `changed_fields`, and the optional decrypted `edit_reason`. It never returns ciphertext or prior/current business payload values. Access requires a live Provider session, exact Provider Host/Origin, CSRF protections, recent step-up, and either the original requester with `company.provision` or a distinct current reviewer with `provider.approval.review`. The database query is operation-scoped and protected by FORCE RLS; the reviewer policy denies the original requester even if that identity also holds reviewer capability. Authorized owners/reviewers can read this limited history after approval or revocation while their account and capability remain active. Reading history grants no mutation rights. Use `limit` (1–50) and optional `before_revision` for bounded pagination. An independent auditor has no reason-history access because this repository has no existing, narrower audit authorization contract; no audit permission was added.

Stored reasons use the existing `APP_KEY`. There is no new key-rotation mechanism in this change; replacing the key without a compatible prior-key decryption procedure makes these annotations unreadable. Do not log or render reason text as HTML/Markdown. A future UI must escape it as untrusted text. Laravel decrypt failures return a generic safe Provider error and never expose ciphertext or crypto details.

When a slug changes, the edit checks other pending/ready operations on the control connection and checks active registered hostnames through the existing restricted hostname resolver. A detected collision is rejected before the revision changes. A simultaneous new reservation can still race this check; execution retains the final unique hostname/slug constraint and rolls back atomically on conflict.

`GET /api/v1/super/approvals` exposes the current non-secret provision payload, revision, digest and expiry to a caller with `provider.approval.review`. Independent approval or rejection of a provision request requires `expected_revision`; an out-of-date number returns a conflict. The reviewer must inspect the current list again after an edit. The original requester can `POST /api/v1/super/approvals/{approval}/revoke` with a reason and ticket while both rows are pending, using `company.provision` without reviewer capability. Withdrawal atomically marks the approval `REVOKED` and operation `CANCELLED`. Approved, expired, consumed, rejected and executed requests cannot be withdrawn or edited. Execution checks the approved decision revision and current digest before provisioning.

Migration 28 is forward-only because dropping revision history or restoring pre-revision approval semantics could re-enable stale approvals. Use a reviewed forward correction if a deployed database needs repair. The migration gives the Provider authentication role only a column-level, non-secret operation projection; the control role receives narrow revision history read/insert grants under forced RLS. The application reviewer capability check remains required.

The historic founder-invitation tables and legacy methods remain for migration compatibility, but no founder-acceptance route is registered and the V1 provisioning path does not call them. They are not an alternate activation flow.

## Recovery

Recovery operations bind tenant, successor, mode, compromised membership, reason, and ticket into the same digest/idempotency/approval lifecycle. Only `ACTIVE` or `SUSPENDED` tenants qualify. `SUSPENDED` remains suspended; `PROVISIONING` and `ARCHIVED` are denied. The successor must be active, verified, and have no active membership elsewhere. An optional compromised membership is suspended only after the successor's effective `company.administer @ ALL_TENANT` grant is proven. Tenant-first locking serializes recovery with last-admin changes.

## Runtime connections

`pgsql_provider` remains the 10B authentication/session connection. `pgsql_provider_control` is a separate control-plane credential. `pgsql_onboarding` may INSERT only `id,email,password,email_verified_at,created_at,updated_at` on `users`; defaults supply ACTIVE status and auth version. Never use the migration owner in an HTTP process. Runtime roles must be non-owner, non-superuser, non-BYPASSRLS and have no schema CREATE. Provider auth has no tenant-table grants. Provider-control tenant access depends on exact transaction-local operation, approval, action, tenant, provider, capability, MFA, auth-version, and step-up facts.

The direct first-admin path additionally requires a pre-provisioned `daleel_provider_first_admin_writer` group role with `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB`, and `NOCREATEROLE`. The additive migration validates this role but neither creates it nor grants it to a login. The `pgsql_provider_control` login must be explicitly granted membership in this group and the existing, separate `daleel_provider_registry_writer` group. Do not merge or broaden the registry writer. The first-admin role receives only the required column-level reads/inserts and tenant status update. RESTRICTIVE policies narrow its ability to insert a tenant, company_admin role, or matching template grants to the exact active approved operation. Existing FORCE RLS remains enabled.

`PROVIDER_API_HOSTS` is a comma-separated exact Host-authority list (case-insensitive, no wildcards); keep it empty until the deployment owner registers the Provider API host. `PROVIDER_ALLOWED_ORIGINS` remains the independent browser Origin allowlist.

The frozen seat policy says the first Company Admin counts as one seat. Subscription/capacity storage and enforcement are not implemented in the bounded source; this control does not invent a plan or cap. Before seat-consuming staff operations are enabled, a separate authorized commercial implementation must enforce Provider-owned capacity transactionally.

The disposable proof uses PostgreSQL 16 and dedicated `daleel-crm-b10c-*` resources. Runtime role grants are environment provisioning, not migrations. Recreate least-privilege grants after recreating 10C tables; do not grant table ownership or broad privileges to make a request pass.

## Operations and release boundary

Rate limiting supplements capability checks; it is not authorization. The request id remains the support correlation key. Audit and outbox writes must share the business transaction; either failure rolls it back. No purge is configured. Production audit retention and commercial eligibility remain owner-policy gates. No automatic release, deployment, provider onboarding, or next batch follows this foundation.
